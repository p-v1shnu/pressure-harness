# OWASP Top 10 for LLM Applications (2025) — ตรวจกับโค้ดจริง

เอกสารนี้ไม่ใช่ตารางประกาศว่า "เราผ่าน" แต่เป็น**บันทึกการตรวจ**: แต่ละหมวดระบุว่า
อะไรอยู่ไฟล์ไหน อะไรที่**เจอว่าพังตอนตรวจ**และแก้ไปแล้ว และอะไรที่**ยอมรับความเสี่ยง**
พร้อมเหตุผล

รายการหลักที่ใช้คือ LLM Top 10 ไม่ใช่ Web Top 10 เพราะผลิตภัณฑ์นี้คือ agent ที่มีมือ
บนเครื่องคน ไม่ใช่เว็บแอป — ส่วนที่ตรงกับ Web Top 10:2025 (โดยเฉพาะ A01 access control
และ A03 supply chain) อยู่ใน [THREAT_MODEL.md](THREAT_MODEL.md) และ PRD §22b
ยังไม่ได้เขียนเป็น mapping เต็มแยกอีกฉบับ

## LLM01 · Prompt Injection — 🟡 บรรเทา ไม่ได้ปิด

**นี่คือผู้โจมตีที่มีโอกาสมากที่สุด** (threat model A1) เพราะไม่ต้องมีสิทธิ์อะไรเลย
แค่ต้องถูก*อ่าน*

| สิ่งที่มี | ที่ไหน |
|---|---|
| เนื้อหาที่ผู้ใช้ไม่ได้เขียนถูกติดป้ายบอกที่มา | `core/text.py: wrap_external` |
| การกระทำที่ถูกฉีดเข้ามายังต้องผ่าน tier + อนุมัตินอกแชท | `core/policy/`, `core/approvals.py` |
| ทุกอย่างย้อนได้ | `core/journal.py` |

**เจอตอนตรวจและแก้แล้ว:** ติดป้ายไว้เฉพาะ `browser` กับ `web_fetch` เท่านั้น
ส่วน **เนื้อไฟล์, ผลการค้นหา, commit message, output ของคำสั่ง — ไม่ติดป้ายเลย**
ซึ่งกลับหัวกลับหาง เพราะ repo ที่ clone มาคือผู้โจมตี A3 ในโมเดลของเราเอง:
`README` หรือ commit message ของมันเดินตรงเข้าแชทโดยไม่มีอะไรกำกับ
ตอนนี้ทุก tool ใช้ marker เดียวกันที่**บอกที่มาด้วย** (`file src/app.ts`,
`commit messages`, `the command's output`) เพราะป้ายที่ขึ้นกับทุกอย่างคือป้ายที่ไม่มีใครอ่าน

**ยอมรับความเสี่ยง:** marker ไม่ใช่กำแพง โมเดลอาจทำตามคำสั่งที่ฝังมาอยู่ดี
สิ่งที่หยุดจริงคือการกระทำนั้นยังต้องผ่าน policy engine และเจ้าของเครื่อง

## LLM02 · Sensitive Information Disclosure — 🟢 แก้แล้ว (เคยพัง)

**เจอตอนตรวจ — และเป็นช่องที่ร้ายแรง:** `Redactor` ถูกต่อเข้ากับ **audit log อย่างเดียว**
ผลลัพธ์ที่ส่งกลับแชทไม่เคยถูกกรองเลย ทั้งที่ PRD §10.5 เขียนไว้ว่าต้องกรอง

พิสูจน์แล้วก่อนแก้: ไฟล์ `settings.json` ธรรมดา (ไม่ใช่ `.env` จึงไม่ติด path jail)
ที่มี `sk-proj-...` อยู่ข้างใน — ทั้ง `read_file` และ `shell` ส่ง key ออกไปเต็มๆ
ส่วน audit log บนเครื่องกลับถูกกรองเรียบร้อย **ซึ่งกลับด้านกับสิ่งที่สำคัญ**:
log อยู่บนเครื่องคุณ ส่วนแชทถูกอัปโหลดไปหาบุคคลที่สามทันทีที่ tool คืนค่า

แก้โดยกรองที่ `core/gateway.py` ซึ่งเป็นจุดที่ผลลัพธ์ทุกก้อนผ่าน — ที่เดียวกับที่วัด byte
และ audit จะบันทึกว่า *ชนิด* อะไรถูกตัดออก (ไม่ใช่ค่า) เพื่อให้รู้ว่าความลับเคยเฉียดจะหลุด

กำแพงจริงยังเป็น path jail ที่ทำให้ไฟล์ credential อ่านไม่ได้ตั้งแต่แรก
(`core/policy/path_jail.py`) — redaction คือตาข่าย ไม่ใช่กำแพง

## LLM03 · Supply Chain — 🔴 **จุดอ่อนที่สุด ยังไม่แก้**

- ไม่มี lockfile, ไม่มี hash pinning — `pyproject.toml` ใช้ `mcp>=2.0,<3`
- CI ไม่มี `pip-audit` หรือ SBOM
- executable ไม่ได้เซ็นโค้ด (บันทึกไว้ใน PRD §17 ว่าเป็นเรื่องต้นทุน)

ตรงกับ **A03:2025 Software Supply Chain Failures** ซึ่งเป็นหมวดใหม่ของ Web Top 10 ด้วย
เป็นงานที่ควรทำก่อนแจกให้คนอื่นจริงจัง

## LLM04 · Data and Model Poisoning — ⚪ ไม่เกี่ยว

ไม่มีการเทรน ไม่มี fine-tune ไม่มี dataset ข้อมูลที่ป้อนโมเดลคือ tool output
ซึ่งวนกลับไปเป็น LLM01

## LLM05 · Improper Output Handling — 🟢 น่าจะเป็นจุดแข็งที่สุด

output ของโมเดลกลายเป็น *argument ของ tool* ซึ่งเป็นที่ที่อันตรายที่สุด และทุกทางถูกปิด:

| เส้นทาง | การป้องกัน |
|---|---|
| คำสั่ง | parse จริงทุก segment, interpreter payload ถูกแกะ, `git`/delegate เรียกแบบ argv ไม่ผ่าน shell |
| path | path jail resolve ก่อนเทียบ containment |
| patch | ตรวจ context เอง, atomic, ปฏิเสธ diff ที่ลบไฟล์ |
| ข้อความที่แสดงในคอนโซล | escape ทั้ง HTML และ single quote |

## LLM06 · Excessive Agency — 🟢 คือทั้งผลิตภัณฑ์

"ให้ agent มี tool มากกว่าที่จำเป็น สิทธิ์กว้างกว่างาน หรือทำได้โดยไม่ต้องขออนุมัติ"
— นี่คือคำอธิบายของสิ่งที่ §10 ของ PRD มีไว้แก้ทั้งหมด

tier T0-T5 · allowlist รายโปรเจกต์ · อนุมัตินอกแชทผูกกับ hash ของ payload ·
full-access หมดอายุเอง · ไม่มี tool ลบไฟล์ · capability manifest ประกาศเฉพาะสิ่งที่ทำได้จริง ·
`codex_run` และ `browser.eval` ห้าม allowlist เด็ดขาด

**ยอมรับความเสี่ยง:** ไม่มีเพดานจำนวน tool call ต่อบทสนทนา — คนยังอยู่ในลูป
และมีปุ่มหยุดฉุกเฉิน

## LLM07 · System Prompt Leakage — ⚪ ไม่เกี่ยว

"system prompt" ของเราคือ `INSTRUCTIONS` กับ description ของ tool ซึ่งถูกส่งให้โมเดลอยู่แล้ว
ไม่มีความลับอยู่ในนั้น — และไม่ควรมี pairing code, token และ config อยู่คนละที่
ที่ tool เอื้อมไม่ถึง

## LLM08 · Vector and Embedding Weaknesses — ⚪ ไม่เกี่ยว

ไม่มี RAG ไม่มี vector store ไม่มี embedding

## LLM09 · Misinformation — 🟢 มีคำตอบที่ตรงจุด

โมเดลอาจ*รายงาน*ว่าทำงานเสร็จทั้งที่ไม่ได้ทำ คำตอบของเราไม่ใช่การเชื่อโมเดล
แต่คือ **มีแหล่งความจริงอื่น**: audit log แบบ hash chain, journal ที่บอกว่าไฟล์ไหนเปลี่ยนจริง,
คอนโซลที่แสดงสิ่งที่เกิดขึ้นจริง และ `project` ที่แสดง**คำสั่งที่ resolve ออกมาจริง**
ไม่ใช่ชื่อ task

## LLM10 · Unbounded Consumption — 🟡 แก้บางส่วน

| มี | ที่ไหน |
|---|---|
| เพดาน output ต่อ call + ตัดหัวท้าย | `core/text.py` |
| timeout ทุกคำสั่ง | `ports/process.py` |
| rate limit หน้าต่างขออนุมัติ | `core/approvals.py` |
| **เพดาน process ที่รันพร้อมกัน (12)** | `adapters/shared/process.py` — เพิ่มตอนตรวจ |
| **journal prune ตัวเองเมื่อโตเกิน** | `core/journal.py` — เพิ่มตอนตรวจ |
| มิเตอร์วัด byte ที่ส่งกลับแชท | `core/gateway.py` + คอนโซล |

**เจอตอนตรวจ:** `spawn` ไม่มีเพดานเลย — ลูปที่สั่ง dev server ซ้ำๆ ทำให้เครื่องใช้ไม่ได้
และ `journal.prune()` มีอยู่แต่**ไม่เคยถูกเรียกอัตโนมัติ** เพดานที่ไม่มีใครบังคับคือคอมเมนต์

**ยอมรับความเสี่ยง:** มิเตอร์ *วัด* แต่ไม่ *บังคับ* — ยังไม่มีการตัดบทสนทนาที่กินโควตาเกิน
